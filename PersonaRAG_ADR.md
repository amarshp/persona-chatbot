# PersonaRAG Architectural Decision Record

Source of truth: `results/LIVE_STATUS.md`. Supporting implementation and artifacts are in `scripts/`, `v1/`, `shared/data/`, and `results/v1/`.

PersonaRAG is a Fang Yuan persona simulation system for *Reverend Insanity*. The project goal is not "a chatbot with a persona prompt"; it is a system that reasons in the character's decision logic, speech register, and factual world model while being honest about what the current corpus actually grounds.

## 1. Problem Framing

**Context** -> PersonaRAG started with a deliberately narrow but difficult target: make a model answer like Fang Yuan, not just describe Fang Yuan. The raw source is large: 2,334 chapters, roughly 4.75M words and 6.46M tokens by the project's profiling notes. The initial implementation uses chapters 1-120 because they contain a sufficiently formed version of the character while keeping iteration cost, retrieval debugging, and eval runs practical. The live methodology decision was to build evaluation-first: baseline, measure, diagnose, add one component, re-evaluate.

The first architecture was V1 Level 1: `scripts/extract_personality.py` produces three personality artifacts, and `v1/persona/prompt_composer.py` turns them into a four-layer prompt:

- L1 identity core from `personality_dossier.json` and `decision_framework.json`
- L2 speech and behavior rules from `speech_profile.json`
- L3 dynamic novel context, empty at Level 1
- L4 self-state and conversation state

The runtime is intentionally simple: `v1/main.py` loads the prompt composer, keeps the last 8 user/assistant pairs, retrieves optional L3 context, streams a response, and logs usage through `shared/llm_client.py`.

**Options Considered** -> The project explicitly considered two build strategies:

- Start with a complete theoretical pipeline, then tune it.
- Start with the simplest working baseline and add complexity only after a measured failure.

For evaluation, it also considered target-behavior grading generated by Claude itself, but that was rejected as circular: Claude would write the targets, Claude would answer, and Claude would judge. The better test was comparative: response A uses a bare Fang Yuan system prompt, response B uses the full extracted persona prompt, and a different judge model scores both.

For data scope, the options were full 2,334-chapter ingestion immediately or an MVP subset. Full ingestion would be more complete but much slower to debug. A 120-chapter MVP would miss later canon but make every failure inspectable.

**Decision + Reasoning** -> The project chose the evaluation-driven path and the 120-chapter MVP. That was the right engineering choice because the unknown at the beginning was not "can we build a big RAG stack"; it was "which parts of this stack actually improve the persona." Building all components up front would make failures hard to attribute.

The eval stack became comparative first, then canon-specific later. The initial A/B eval showed the full prompt was earning its cost: after the first baseline, B won about 72% of dimension decisions over the bare prompt. After the L2 brevity fix, B win rate rose to about 76%, and all four scored dimensions cleared their stopping thresholds:

- specificity: about 3.95/5
- speech fidelity: about 4.00/5
- anti-sycophancy: about 4.80/5
- depth: about 3.60/5

That result justified keeping the extracted personality architecture instead of falling back to "the base model already knows Fang Yuan."

**What We Learned** -> The biggest early lesson was that a good persona system needs two kinds of measurement. Broad A/B evals can tell whether the architecture adds value over a bare role prompt. Canon QA can tell whether the system knows and uses the actual novel facts. The first answered "is L1/L2 useful?" The second exposed "L3 is empty or incomplete."

The second lesson was that stopping conditions matter. The project found real defects in L2, fixed one, and stopped when the dimensions cleared threshold instead of endlessly prompt-tuning. That restraint mattered later, when retrieval and anti-fabrication failures became separate, measurable workstreams.

## 2. Data Pipeline Decisions

**Context** -> The source EPUB is treated as a structured archive, not as one text blob. `scripts/extract_subset.py` opens `Reverend_Insanity.epub` as a ZIP, reads chapter XHTML files, cleans them with BeautifulSoup, removes translator/editor artifacts, falls back to `chapter_names_from_online.txt` when EPUB chapter titles are weak, and writes clean UTF-8 chapter files into `shared/data/raw/chapter_XXXX.txt`. It also writes `shared/data/raw/manifest.json` with chapter number, title, word count, and filename.

The local MVP corpus currently contains 120 raw chapter files. The manifest totals 243,601 words, with chapter sizes ranging from 1,362 to 3,241 words. The live notes estimate about 300K tokens for chapters 1-120.

Personality extraction uses a two-round pipeline:

- Round 1: evidence extraction into `shared/data/personality/evidence_cache.json`
- Round 2: synthesis into `personality_dossier.json`, `speech_profile.json`, and `decision_framework.json`

The final evidence cache for the 120-chapter MVP contains 1,219 total entries: 631 personality evidence entries, 318 speech evidence entries, and 270 decision evidence entries. It is about 103K tokens, so the three synthesis calls can each consume the full cache.

**Options Considered** -> The main data decisions were:

- Use Haiku for evidence extraction to save money, or use Sonnet for quality.
- Batch evidence extraction at 40 chapters per call, 20 chapters per call, or one chapter per call.
- Build the wiki from `evidence_cache.json`, or from raw chapters.
- Design only for the 120-chapter MVP, or design a path that later scales to 2,334 chapters.

The Haiku/Sonnet experiment was important. Haiku worked at 20 chapters but failed at 40-chapter scale by ignoring JSON structure and returning prose. Sonnet was slower and more expensive but produced richer evidence, stronger speech capture, and better second-order reasoning. The live cost comparison estimated the full-book Sonnet path around $24 and Haiku around $7.70, but the $16 savings was judged a bad trade because personality fidelity is the core product value.

The evidence-cache-to-wiki shortcut was also rejected. Evidence cache entries are psychometric proof fragments. Wiki pages need scene-level context: situation, stakes, dialogue, action, reasoning, and consequences. Using trait-selected excerpts would create thin pages that retrieve on the right words but fail to ground actual answers.

**Decision + Reasoning** -> The project kept Sonnet as the extraction model and settled on 20-chapter evidence batches. This matched the observed reliability boundary and kept the output structured. For the MVP, the 103K-token evidence cache is one-shot synthesizeable. For the full 2,334 chapters, the project designed but did not yet implement a Phase 1.5 aggregation layer:

- extract evidence in roughly 117 calls of 20 chapters each
- normalize free-form trait/pattern/situation labels
- cluster and deduplicate
- keep the highest-quality quoted evidence per cluster
- compress to roughly 100-150K tokens
- synthesize the same three canonical JSON artifacts

The wiki pipeline was built from raw chapter files, not from the evidence cache. That decision preserved narrative context and made later retrieval failures diagnosable as content gaps rather than artifacts of psychometric pre-filtering.

**What We Learned** -> The data pipeline reinforced a useful boundary: personality data and knowledge data are not the same product. The three JSON files are good at identity, speech, and decision logic. They are not a substitute for a fact base. The LLM wiki and raw chapter chunks exist because the personality cache intentionally discarded many concrete facts that later canon QA needed.

The second lesson was to design for the full corpus without implementing full-corpus machinery prematurely. The MVP extraction works because chapters 1-120 fit into current synthesis limits. The full-book path needs aggregation, but building that before the 120-chapter system proved value would have been speculative complexity.

## 3. Retrieval Architecture Decisions

**Context** -> Novel grounding was the first major gap after L1/L2 passed their broad eval thresholds. Level 1 had no L3 context, so it could sound like Fang Yuan but could not reliably answer canon-specific questions. The project first explored an LLM Wiki: topic-oriented Markdown pages under `shared/data/wiki/`, indexed by `shared/data/wiki/index.md`, with pages grouped as philosophy, decisions, relationships, and events.

The wiki started as the simplest useful grounding layer. It now has 24 pages covering chapters 1-120. The page format was intentionally not a chapter summary. Each topic page stores pre-synthesized context: key events, Fang Yuan's reasoning, tags, and related pages. `v1/retrieval/wiki_retriever.py` loads the pages, tokenizes the query, scores by keyword overlap, and formats the top sections into L3.

As canon QA became stricter, the wiki exposed its limit: curated summaries are high signal but lossy. They omitted facts like "Chinese scholar", "Qing Mao Mountain", "passers-by / scram", Rank 3 exit threshold, and some cultivation-speed constraints. These facts exist in the raw chapters but were compressed out of the wiki.

**Options Considered** -> The retrieval path evolved through several options:

- LLM Wiki only: high precision, cheap, debuggable, but incomplete.
- Vector RAG only over raw chapters: complete, but noisier and harder to inspect.
- LLM Wiki plus raw chapter retrieval: preserve curated summaries while adding literal fact coverage.
- Multi-query expansion: use an LLM to rewrite the user query into retrieval-oriented phrasings.
- CRAG-style filtering: retrieve broadly, then filter for relevance.
- LLM-as-judge CRAG vs local cross-encoder reranking.
- BM25 score blending vs using lexical/BM25 only as candidate generation.

The project also debated sequencing. Multi-query looked like a temporary bridge that embeddings might later replace, but the empirical retrieval failures were about both vocabulary mismatch and candidate noise. The eventual design used multi-query and CRAG because they solved different measured problems.

**Decision + Reasoning** -> The shipped retrieval stack is additive:

```text
user query
  -> query router
  -> multi-query rephrasings
  -> wiki keyword retrieval
  -> raw chapter vector retrieval via Chroma
  -> merge candidates
  -> BAAI/bge-reranker-base cross-encoder CRAG filter
  -> L3 context
  -> persona prompt
```

Implementation details:

- `v1/retrieval/multi_query.py` generates three rephrasings and preserves anchors like names, places, Gu names, ranks, and metaphors.
- `v1/retrieval/chapter_retriever.py` wraps the ChromaDB collection `fang_yuan_chapters`, returning raw chapter chunks as `WikiSection` objects so the downstream formatter and CRAG code do not need a second candidate type.
- `v1/retrieval/crag_filter.py` replaced the LLM relevance judge with `BAAI/bge-reranker-base`, using a 0.5 threshold and max scoring over original query plus sub-queries.
- `v1/main.py` and `scripts/run_canon_qa.py` bumped `k_max` to 30 so both wiki and chapter candidates can reach the reranker.

The cross-encoder decision was especially important. Earlier LLM-as-judge scoring had temp=0 instability and produced inconsistent binary decisions. Relevance scoring is a local reranker problem, not a chat-model problem. A cross-encoder is deterministic, cheaper, and trained for query/passage relevance.

BM25 score blending was rejected. It would mathematically lift chunks with lexical overlap even when the cross-encoder judged them semantically weak. That creates false positives. Lexical retrieval is useful for candidate generation; the cross-encoder remains the relevance arbiter.

**What We Learned** -> Retrieval improved, but it did not solve every canon QA failure. The Phase 2 chapter retrieval run on six wiki-gap questions recovered 2/6:

- Q02 passed because raw chapter retrieval surfaced the Earth/Chinese scholar fact.
- Q05 passed because chapter retrieval found the "passers-by / scram" reasoning.
- Q01 still failed because it required multi-chunk synthesis: the death-scene chunk and the named Qing Mao Mountain rebirth chunk needed to be connected.
- Q07, Q14, and Q15 had the right facts in L3 and even in the model's internal reasoning, but the spoken answer compressed out rubric-required specifics.

That shifted the diagnosis. Some failures were no longer retrieval failures; they were generation-compression failures. The model had the evidence but the L2 rule "spoken is short" caused it to omit canonical facts from the public answer.

The second retrieval lesson was negative but valuable: retrieval score is not answer presence. A later retrieval-state experiment tried to mark L3 as `NO_GROUNDING`, `WEAK_GROUNDING`, or `STRONG_GROUNDING` based on CRAG scores. It failed because the cross-encoder scored topically related chunks highly even when they did not contain the requested answer. Q20 retrieved high-scoring demonic-path chunks but none contained the sect name; the model interpreted `STRONG_GROUNDING` as license to fabricate. The change was reverted.

## 4. Persona Layer Decisions

**Context** -> The persona layer is where the project tries to encode "how Fang Yuan thinks" separately from "what facts are available." The three personality JSONs are the stable substrate:

- `personality_dossier.json`: psychometrics, values, contradictions
- `speech_profile.json`: vocabulary, sentence structure, internal/external voice, anti-patterns
- `decision_framework.json`: axioms, risk logic, people assessment, decision patterns, forbidden moves, Earth analogies

`prompt_composer.py` turns these into a large L1/L2 system prompt and enforces a two-part response format:

- `<internal>`: private continuous reasoning
- `<spoken>`: the actual line Fang Yuan says

This split became load-bearing. It lets the model reason in detail while keeping public speech terse. It also made later failures easier to diagnose because some canon-required facts appeared in `<internal>` but disappeared from `<spoken>`.

**Options Considered** -> The persona layer went through several choices:

- Keep the full extracted JSONs in prompt, or prune aggressively.
- Make speech extremely terse, or allow analysis length when dismantling premises.
- Let the model answer naturally, or force `<internal>` and `<spoken>` tags.
- Patch failures with exact forbidden phrases, or define general failure modes with multiple probes.
- Add anti-fabrication examples close to canon QA questions, or avoid examples that contaminate the eval.

The project initially over-constrained terseness. In speech anti-pattern probes, the full prompt sometimes underperformed the bare prompt because it answered emotional hooks with empty brevity. The fix was not to make Fang Yuan warmer; it was to clarify that brevity constrains warmth, not substance. When diagnosing a premise, he can be expansive; when speaking aloud, he must still land the conclusion coldly.

Boundary failures were also handled as named modes rather than one-off patches: lecture-monologue, external-morality leakage, and "idea not mind" style drift. This avoided token-level overfitting like "never say legal/theft/dirty" and instead targeted the behavioral failure.

**Decision + Reasoning** -> The project kept the full L1/L2 prompt for the MVP because there was not yet evidence for what could be safely compressed. The prompt was modified only after measured failures. The most important persona decisions were:

- Keep `<internal>` and `<spoken>` as a hard output contract.
- Strengthen L2 to distinguish "cold" from "empty".
- Add anti-sycophancy and external morality rules so the model evaluates exposure, payoff, and position rather than conventional ethics.
- Add anti-fabrication discipline: any specific name, date, quote, sequence, number, place, technique, organization, or event must be grounded in L3 or prior conversation.
- Treat modern Earth problems through the same structural logic, but later reduce corporate vocabulary after chat transcripts showed "ruthless executive coach" drift.

The contamination issue was the key methodology correction. A few-shot anti-fabrication example asked almost the same shape as canon QA Q20: the name of Fang Yuan's demonic sect or organization. Q20 passed after that example, but the answer was near-verbatim template copying. That made Q20 an in-distribution prompt, not a fair generalization test.

The project corrected this by:

- reverting the sect-name few-shot
- strengthening the general anti-fab rule
- caching canon QA multi-query rephrasings so retrieval became deterministic
- creating `shared/data/eval/canon_qa_holdout.md` with three locked anti-fab probes: quotation, date, and ordered sequence
- replacing another near-contaminating emotional-bait example that mirrored Q09

The result was honest. Q20 regressed when the overfit example was removed, proving the prior pass was inflated. The holdout set went 3/3 PASS, showing the generalized rule works for several non-mirrored shapes.

**What We Learned** -> Persona work is vulnerable to two forms of false progress:

- Prompt examples can teach the model to copy an eval answer instead of generalizing a rule.
- LLM judges can flip verdicts on semantically similar answers if the rubric is vague.

The project responded by improving the eval substrate, not just the persona prompt. `results/v1/NOTES_2026-05-04_anti_fab_overfit_diagnosis.md` documents the de-overfit process. Rubrics in `canon_qa_v1.md` were sharpened to specify literal requirements, optional elements, paraphrase tolerance, and anti-pattern disqualifiers. The revised honest baseline became about 10/19 on canon QA, not the inflated 11/19. That is less flattering, but more useful.

The multi-turn chat simulator later showed a practical improvement. After the L2 voice fixes, a Codex review scored the transcript 8.0/10, then 8.4/10 after reducing corporate-strategy register and increasing predation/food-chain framing. The remaining gap is not basic character failure; it is that the scaffold can still sound like modern workplace consulting with cultivation language attached.

## 5. What's Left and Why

**Context** -> The current system has real architecture in place: cleaned raw chapters, personality JSONs, an L1/L2/L3/L4 prompt architecture, wiki retrieval, raw chapter vector retrieval, multi-query expansion, cross-encoder filtering, canon QA, holdout anti-fab probes, and chat transcripts. It is not production-ready by its own thresholds. The latest reliable canon QA framing is roughly 10/19 before Phase 2 chapter retrieval, with the targeted Phase 2 wiki-gap run recovering 2/6. The live notes explicitly held off on a full canon QA rerun after Phase 2.

The current Chroma chapter store also has known limitations: it covers chapters 1-114, not 1-120; chunks have no overlap; some translator/footer noise remains. The wiki covers 1-120 but is lossy. L4 state is present but still simple. Full 2,334-chapter scaling is designed but not implemented.

**Options Considered** -> The remaining work could go several directions:

- Keep tuning L2 for generation compression.
- Add a per-question wiki patch for known anti-fab failures like Q20.
- Add retrieval-state signaling.
- Add post-generation span-level verification.
- Rebuild raw chapter chunks with overlap and full 1-120 coverage.
- Run the full canon QA after Phase 2 to quantify regressions.
- Scale the pipeline to all 2,334 chapters.

Some options were tested and rejected. Retrieval-state signaling was reverted because topical relevance was mistaken for answer presence. A per-question wiki page saying "the previous-life sect name is not recorded" would fix Q20 but not the class of problem. Span-level verification would generalize, but it requires an extra LLM call per response and is outside the current minimal-design budget.

**Decision + Reasoning** -> The honest stopping point is to keep the current stack, document the known limits, and prioritize the next work by leverage:

1. Rebuild chapter chunks with overlap and chapters 115-120 included. This fixes a known data-quality issue without changing architecture.
2. Run a full canon QA after the Phase 2 retrieval changes. The targeted 2/6 recovery is useful but not enough to claim global improvement.
3. Address generation compression in L2. Q07, Q14, and Q15 show the model often has the right facts internally but omits them from spoken output. The fix likely belongs in `prompt_composer.py`: grounded specifics that appear in L3 and matter to the question must survive into `<spoken>` even when the line is terse.
4. Treat Q20-class fabrication as a known limit unless it becomes product-critical. The general fix is answer-presence or span-level verification, not a one-off wiki patch.
5. Only after the 120-chapter system is stable should the project implement the 2,334-chapter aggregation path.

**What We Learned** -> The core interview story is that PersonaRAG's architecture grew from measured failures:

- Prompt-only worked for voice and reasoning but failed novel grounding.
- Wiki retrieval worked for curated high-signal knowledge but dropped literal facts.
- Raw chapter retrieval recovered some missing facts but introduced generation-compression and multi-chunk synthesis problems.
- Cross-encoder CRAG made relevance deterministic but did not prove answer presence.
- Few-shot prompt fixes can contaminate evals if they mirror the test set.
- A lower score after de-contamination can be a better engineering result than a higher contaminated score.

The system is at a useful prototype stage: strong enough to demonstrate the persona architecture and retrieval path in an interview, not yet strong enough to claim robust canon-grounded production behavior. The best next step is not a larger architecture diagram. It is tightening the remaining measurable failure clusters without erasing the hard-won separation between persona, retrieval, data, and evaluation.
