## Interpretation

The previous hypothesis ("section is too coarse, sub-chunk it on `**bold (Ch N):**` markers") was wrong. The smoking gun is Phase 4c: even an ideal isolated subchunk still scores 3 when paired with the original Q03 query. The problem is not the section. The problem is the query.

Q03 has three clauses:
1. "exactly how many steps did you walk into the flower sea"
2. "what grade did that put you at"
3. "what is the grade scale"

The judge anchors on clauses 1–2 ("you walked", "did that put YOU at"), reads them as the primary intent, and treats clause 3 as a side request. A section that does not directly answer "how many steps did *Fang Yuan* walk" is judged largely irrelevant — even when it contains a complete answer to clause 3. Phase 4a confirms the symmetric effect: when the query is rewritten to lead with the scale clause, the same section scores 10.

A secondary problem: Phase 3's spread of 4 at temp=0 means CRAG is structurally noisy on marginal cases. A single eval rep can decide PASS/FAIL by chance.

## What this means for the fix path

**Sub-chunking is no longer the right fix.** Spending engineering on it would not move Q03.

**The actual root cause is upstream of CRAG:** the multi-query stage. Current MQ rephrases the *full multi-clause query* into other multi-clause queries — all carrying the same FY-anchor bias. None of the three rephrasings produced for Q03 isolated the scale clause.

Two viable paths, in ascending complexity:

1. **Cheap: query decomposition in MQ.** Change the MQ prompt from "rephrase using different vocabulary while preserving exact meaning" to "decompose multi-clause questions into atomic sub-queries; for each sub-query also produce one vocabulary variant." For Q03 this would generate sub-queries like *"What is the grade scale at the awakening ceremony?"* — which Phase 4a proves CRAG would score 10 on the right section. Implementation is one prompt change in `multi_query.py`.

2. **Structural: replace CRAG LLM-judge with a cross-encoder reranker.** Phase 3's spread=4 at temp=0 is a structural defect of using a chat-tuned LLM as a relevance scorer. Cross-encoders (e.g. `BAAI/bge-reranker-base`) are trained on `(query, passage, relevance)` triplets and are deterministic on CPU. This was already on the table per the earlier discussion with Claude Desktop. It would address both the QUERY_ANCHOR and the NOISE findings simultaneously.

Recommended order: (1) first — cheapest test of whether better queries fix Q03/Q07/Q08-class failures. If (1) yields the gain, (2) becomes optional polish. If (1) doesn't yield, (2) is justified.

**Drop the sub-chunking proposal from the previous diag.** It would have been a wrong investment.
