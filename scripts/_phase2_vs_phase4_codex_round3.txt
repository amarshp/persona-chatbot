FOLLOW-UP ROUND 3 — user pushback

The user is calling out a hidden assumption in your Path D recommendation. Quote: "just because the plan says multi-query will be removed doesn't mean it will. We're doing incremental building. If multi-query does the job then we may not need BGE."

This is the strict eval-driven principle (Sculley, Karpathy, Google's Rules of ML) applied properly: never invest in a harder solution if the simpler one might suffice — measure first.

Re-examining your Path D under this lens:

1. Your "multi-query is least durable" argument requires us to believe BGE will dominate it on THIS corpus. We have no evidence for that. Both are vocabulary bridges:
   - Multi-query: LLM general-knowledge paraphrasing
   - BGE: learned semantic embeddings
   For a Chinese-cultivation novel with neologisms (Gu, Liquor Worm, Spring Autumn Cicada, Aperture), neither is obviously better. The plan's assumption that BGE deprecates multi-query is itself an unmeasured claim.

2. Cost: 1 rephrase call/turn at JUDGE_MODEL = ~1k input + ~100 output tokens ≈ $0.001/turn. For a persona chatbot, total recurring cost is pennies. The "sticky cost forever" concern is theoretically real but quantitatively negligible.

3. Implementation cost: multi-query is ~50 LOC + one prompt template + a list-of-phrasings JSON parse. BGE requires embedding model load, vector persistence (numpy or chroma), startup-time cost, and matching infra. Multi-query is materially smaller to implement.

4. Critically: the user's failure case ("paraphrase queries miss") is precisely what multi-query was invented to solve. The whole T02 technique exists because keyword retrieval misses paraphrases. We are deliberately discarding the canonical solution because we suspect a different solution might be better — without measuring.
